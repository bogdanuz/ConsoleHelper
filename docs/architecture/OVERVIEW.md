## Потоки данных

### In-page DOM

`words/cells → buildGrid → normalizeRows → Table Studio → export`

### Hub paste

`clipboard HTML/TSV/CSV → parseClipboard → normalize → Table Studio / hub preview → export`

## Почему shared core на TypeScript

Алгоритмы тестируются в Node (Vitest).  
In-page tools на старте могут дублировать мини-копии; цель Sprint 1–2 — либо codegen из shared, либо тонкие обёртки. Не ломать возможность вставить один `.js` файл.

## Контракт tool

`tools.json`:

```json
{
  "id": "text-to-table",
  "name": "Текст → таблица",
  "file": "text-to-table.js",
  "tag": "данные",
  "desc": "Область или вся страница по координатам слов"
}
```

Каждый `public/tools/*.js`:

- IIFE, без обязательных глобальных зависимостей (кроме явно документированных CDN).
- Идемпотентен: повторный запуск уничтожает предыдущий UI (`window.__ch_*`).
- Не трогает данные страницы, только читает (кроме временного overlay).

## Нормализация (главная боль скриншота)

Проблема: визуально одна запись = две текстовые линии → две строки сетки.

Стратегии (по приоритету):

1. **DOM mode:** брать `innerText` ячейки целиком, split `\n` → колонки `name` / `id`.
2. **Spatial mode:** если ряд имеет мало колонок и следующий ряд «похож на id» (короткий, паттерн `PJ-…` / код) и выровнен под name-колонку — merge.
3. **Manual:** в preview объединить выбранные строки.

Подробности — скилл `table-normalize`.

## Безопасность

- Нет сервера → данные остаются в браузере.
- Внешний `eval` загрузчика = trust к своему репо; не давать write-доступ чужим.
- Чувствительные данные: предпочтительно full-code snippet без сети, если политика требует. В репо — только обезличенные демо.
